# E-04 — Debug kit (`Tools/plasmid-debug`) and private engine runtime

**Status:** in progress (T-01 scaffold and T-02 console spike done 2026-10-26; T-03 done 2026-10-26; next T-04) · **Components:** code, tools · **Estimate:** unestimated · **Updated:** 2026-10-26
Origin: Lucio asked (2026-10-26) to bring what SandboxLLM learned (private engine, console/startup commands, remote control) to FPS and to wrap the debug features as a reusable lib. Prior art: `Projects/SandboxLLM` (`.engine-private`, `snl_*` commands in `Code/GamePlugin.cpp`, MCP `console`/`observe`/`set_run_environment`).

## Goal
FPS runs against its own private Debug engine copy, and a shared, versioned lib `Tools/plasmid-debug` gives any CRYENGINE game plugin: render debug views, screenshots, a debug menu, `plasmid_debug_*` commands inside the **engine's own console**, pause, free camera, camera locks, sky/time and weather debugging.

## Decisions
- **Extend the engine console, do not build one** (Lucio, 2026-10-26). `IConsole` already offers `AddCommand`, `RegisterAutoComplete`, `AddOutputPrintSink`, `AddConsoleVarSink`, `ShowConsole`. The kit registers `plasmid_debug_*` commands with per-argument autocomplete and `plasmid_debug_help`. Fallback to a custom overlay only if the engine console fails on Linux (see T-02 findings).
- **Shared tool, not copy-paste:** `Tools/plasmid-debug` (own git, `VERSION`, `CHANGELOG.md`, tag `vX.Y.Z`); projects use a tagged vendored copy that is never edited (same model as `Tools/plasmid-dev` and `Tools/plasmid-assets`). C++ half is a CMake fragment compiled into the game plugin; Python half (optional) drives the same commands over the Remote Console.
- **Everything is a console command or CVar** so the dropdown console, Remote Console, MCP `console` tool and `+cvar` launch args all reach it the same way.
- **Engine stays read-only** for this epic (same rule as SandboxLLM): gaps become handoff notes to the Crytek domain.

## T-02 findings
Spike = `Tools/cry-debug` console skeleton (`dbg_help`, `dbg_ping`, `dbg_console [0|1|toggle]`, `dbg_keylog`, CVar `dbg_console_key`, argument autocomplete) compiled into `libGamePlugin.so` via a temporary symlink `tools/cry-debug -> ../../../Tools/cry-debug` (to be replaced by a vendored copy in T-14). Run on 5.6.7 Debug, GCC 9, Vulkan, X11, `fps_forest_basin`, 2026-10-26.

**Verified (V):**
- The engine console renders and works on Linux in FPS (`dbg_console 1` via Remote Console, screenshot): scrolling log, input line, the kit's commands.
- `dbg_*` commands registered at `GAME_POST_INIT` are reachable from the Remote Console (`dbg_ping`, `dbg_help`) and from the console's input line.
- Argument autocomplete works: `dbg_console <TAB>` lists `dbg_console 0 / 1 / toggle`. Commands show as `(Command)` in the list.
- Keyboard events reach a plugin `IInputEventListener` (`dbg_keylog 1` prints name/id/modifiers). Our extra key binding works: `dbg_console_key f1` opens and closes the console (`GetStatus` 1 then 0). This is the "new binding" path; no engine change needed.
- Escape with the console open only closes the console; the game keeps running (the player's Escape-to-quit does not fire).
- The tilde key does reach the engine as `eKI_Tilde` (key name `tilde`, id 40), mapped from the physical scancode (`SDL_SCANCODE_GRAVE`), so it is layout independent.

**Not verified (U):**
- A bare physical tilde press toggling the console. The automated test could not make a clean press: on this layout (`us` + `intl` variant) the tilde key is a dead key, so `xdotool` synthesises it with AltGr/Shift held, and the engine ignores tilde with Shift/Ctrl/Alt (`XConsole.cpp:1436`). Lucio's own presses of the real key have no such modifiers. Confirm by hand once: focus the game, press the key left of `1`.
- Plain-prefix TAB completion of command names (engine feature, shown only indirectly).

**Consequences for the plan:**
- Keep the engine console; no custom console needed. `plasmid_debug_console_key` stays as the documented fallback binding (default empty; set e.g. `f1` in the startup config in T-04).
- Console commands must be registered with `ConsoleRegistrationHelper::AddCommand` / `RegisterString` (the `IConsole` registration methods are protected in 5.6.7); the CMake fragment needs the host's `StdAfx.h` (unity "uber" build includes it first).
- The plugin builds with `-std=c++11` and `-Werror`; kit code must stay C++11.
- Test automation: `xdotool` works only when the game window has focus (`windowactivate` + `windowfocus`, check `getwindowfocus getwindowname`); another user's Alt-Tab steals focus mid-test. Prefer Remote Console commands (`../SandboxLLM/docs/findings/data/rc_client.py`) for anything that does not need real key input.

## T-03 findings
Implemented in `Makefile` (project targets) and `.gitignore` (`.engine-private/`). No change to the vendored `tools/plasmid-dev/`.
- `make private-sync`: `rsync` of the shared `bin` and `Engine` plus `system.cfg` and `cryengine.cryengine` into `.engine-private/ce-5.6.7` (**real copies, not hard links**, 1.7 GB; verified different inodes). It leaves our plugin alone and copies no other project's plugin. Re-run it to take a newer shared engine on purpose.
- `make deploy-private`: copies `bin/linux_x64_gcc/libGamePlugin.so` into the private bin (run after every `make build`; `make build` still compiles against and deploys to the shared engine, since headers and CMake live there).
- `make run-private [ARGS=...]`: depends on `deploy-private`, starts the shader server from the shared engine (`make up`), then launches with `CRYENGINE_DIR=CRYENGINE_DIR_56=<private>` and `--no-services`. The dev runner lets a real environment variable beat `.env`, so `.env` still points at the shared engine and `make run` is unchanged.
- `make private-status`: sha256 of `GameLauncher`, `libCrySystem.so`, `libCryRenderVulkan.so`, `libCry3DEngine.so` and the plugin, shared vs private.
- Verified [V]: after `make run-private`, `/proc/<pid>/exe` and the mapped `libCryRenderVulkan.so`, `libCrySystem.so`, `libGamePlugin.so` all come from `.engine-private`; the Remote Console answers `dbg_ping`; `fps_screenshot` saves a correct image of `fps_forest_basin` (identical look to the shared run); the shader server ran from the shared engine as intended. `make stop` stops both.
- Not done / notes: `make status`, `make logs` and `make health` still read the shared engine unless run with the same environment override. The default `make run` stays on the shared engine; switching the default would mean pointing `.env` `CRYENGINE_DIR_56` at the private copy, but a fresh `make configure` needs the shared engine (CMake and headers), which is why SandboxLLM's cached build dir works and a new one would not. Not changed.
- Engine drift to know about: the shared `libCryRenderVulkan.so` now has sha256 `a4e940c165a3...`; SandboxLLM's `docs/engine-baseline.md` pins `996aad96f514` (2026-10-24), so the domain rebuilt it since. Not judged here whether the T9/T10 fixes are still in it (FPS rendered correctly).
- Pre-existing, not caused by the private copy: every run logs the `firstperson.cdf` load errors (E-01/T-01) and some runs then log thousands of `[Error] <CryAssert Linux> Failed to launch assert dialog` lines (`m_pControllerDefinition != nullptr` in `CryDefaultEntities`). A shared-engine run right after the private run logged 2908 of them, the private run 5692, earlier runs 0 to 8266. SandboxLLM's private `system.cfg` sets `sys_asserts=0`; FPS's does not (asserts are real signals in a Debug build, so not silenced).
