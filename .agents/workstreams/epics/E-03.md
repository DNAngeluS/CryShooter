# E-03 — VS Code → `make` migration gaps (starting with debug screenshots)

**Status:** ready (investigation, nothing fixed yet) · **Components:** code, tools · **Estimate:** unestimated · **Updated:** 2026-10-03
Origin: found 2026-10-03, right after `make run` was introduced (356ef7f). The project was built to run from VS Code; `make`/`tools/dev.py` is a new launch path and may differ from it in ways nobody has enumerated.

## Symptom (T-01)
Pressing `K` then `P` in a game started with `make run` produces **no screenshot file**. `game.log`:

```
<22:27:35> [Screenshot] Capturing to user/screenshots/screenshot_20261003_222735.jpg
<22:27:35> bool CryCreateDirectory(const char*): mkdir('/user') failed
<22:27:35> Warning: Frame capture failed!
```
(repeated for 22:27:38 and 22:27:42). `user/screenshots/` still holds only the 11 files from 2026-04-03, which did work — so this path **worked once** (VS Code era, commits `18c160c`–`3ba31dc`).

Facts established:
- `TakeDebugScreenshot()` (`Code/Components/Player.cpp:544`) asks `ICryPak::AdjustFileName("%USER%/Screenshots", …, FLAGS_PATH_REAL | FLAGS_FOR_WRITING)` and its comment assumes an **absolute** result. The logged path is **relative and lower-cased** (`user/screenshots/…`).
- The engine's `CaptureFrameBuffer` code then calls `CryCreateDirectory` on `/user` (it treats the relative path as rooted), which fails for a normal user.
- The directory `user/screenshots/` already exists, so the failure is the path form, not permissions.
- The deployed plugin was rebuilt on 2026-10-03 by `make build`; the working April plugin predates it.

## Hypotheses to test (cheapest first)
1. **Launch environment.** `dev.py run` starts the launcher with `cwd=$CRYENGINE_DIR/bin/linux_x64_gcc`, `stdin=/dev/null`, stdout+stderr redirected to `.dev/logs/game.out.log`, a new session, and the shell env plus `.env`. VS Code's `launch.json` also uses that `cwd` but runs under gdb with an empty `environment`. Compare: `make run` vs `make debug` vs `make run ARGS=…` with `--foreground` from a real terminal vs launching from VS Code. If only the non-gdb path fails, the cause is env/stdio/session.
2. **Engine tree changed since April.** The screenshot fixes depend on engine-source patches (`JpgImage.cpp` `WriteJPG`, `DriverD3D.cpp` `RT_ReadTexture`; see `docs/known-issues.md`) and notes mention the engine directory was renamed (`CRYENGINE_Source` ↔ `CRYENGINE`). Check those patches are present and the engine binaries were rebuilt after them (`git -C $CRYENGINE_DIR status/diff`).
3. **Plugin differs.** April plugin vs today's rebuild: check `git diff 3ba31dc..HEAD -- Code/`. The only known `Code/` change since is `kStartupLevel` + reformat in `GamePlugin.cpp`, so unlikely.
4. **Toolchain differs.** VS Code tasks configure `build/gcc` with the engine's `Linux_GCC.cmake`; the presets used by `make` use the project-local `cmake/toolchain/Linux_GCC_System.cmake`. Rebuild with the VS Code configure command into a scratch dir and diff compile flags/defines.

## Likely fix once understood
Do not rely on `%USER%` expanding to an absolute path. Build the directory from `gEnv->pSystem->GetIProjectManager()->GetCurrentProjectDirectoryAbsolute()` + `/user/screenshots` (the approach commit `18c160c` used), create it with `pFileIO`/`MakeDir`, and pass the absolute path to the capture CVars. Verify by pressing K then P and checking `ls user/screenshots` — **requires a human at the keyboard**; an agent cannot press keys.

Observations for T-01/T-03 (E = evidence observed, I = inferred):
- E: under `make run` the game process `/proc/<pid>/cwd` was the **project dir**, although `dev.py` (`launcher_cmd`) passes the engine `bin/` dir and `launch.json` does the same → the engine chdirs itself. I: that makes cwd an unlikely difference vs VS Code; not observed under gdb or VS Code.
- E: env of the `make run` game: DISPLAY=:0.0, XDG_SESSION_TYPE=x11, HOME/USER normal.
- E: remaining `[Error]` lines in a clean run are the known ones (`firstperson.cdf`, color-grading chart, cvar group duplicates).
- E: shader server logged only 3 connections from the game and no compile activity or errors (shaders were presumably already cached/packed); "connected" alone does not prove a compile works.
- E (hypothesis 2): engine screenshot patches are present (`DriverD3D.cpp` `RT_ReadTexture`/`WriteJPG` call, commit 484946893 TRANSFER_SRC). `libCryRenderVulkan.so` is dated 2026-04-03 23:53, 10 min **before** that commit (2026-04-04 00:03) — consistent with build-then-commit, and screenshots worked on 04-03, so an engine-binary mismatch is unlikely but unproven. `git status` of the engine shows 5 dirty `_ddn.dds` = FPS commit 5bcf131 (intentional) plus 2 untracked files (`entities.json`, `mempalace.yaml`).
- E (VS Code coexistence): `build/gcc` cache = project toolchain `Linux_GCC_System.cmake`, Debug, g++-9 (made by the `gcc9` preset). `.vscode/settings.json` has `cmake.useCMakePresets: always`, so VS Code cmake-tools and `make` share it, and the "CMake Build" preLaunchTask builds the same dir. **Risks (from code, not run):** (1) the manual VS Code tasks "CMake Configure (Debug|Profile)" use the *engine* `Linux_GCC.cmake` into the same `build/gcc`; (2) `make … TYPE=Profile|Release` reconfigures `build/gcc` in place (`do_configure`), flipping VS Code's build type until `make build TYPE=Debug`. I did **not** run VS Code's configure nor a non-Debug `make` mode.
- E: `CRYENGINE/bin` has `linux_x64_gcc`, `linux_x64_gcc_release`, `linux_x64_clang`, `linux_x64_clang_release`; the engine's `ninja -n` wanted to re-run CMake only (no engine rebuild needed observed).
Proposals (not applied; `dev.py` and `.vscode/` untouched): `debug-batch --timeout` should exit 0 (or a distinct code) on timeout and stop the shader server it started; `make status` "deployed" should compare content/size, not mtime; add an engine build target; mark `game.log` runs with a separator; give non-Debug modes their own build dir so VS Code's `build/gcc` stays Debug.
Not covered (needs a human or is unbuilt): K→P screenshot, interactive `make debug`, visual check, `COMPILER=gcc14|clang` (gcc14 also needs two engine header patches, see `workflows/build-run.md`), `make release`.
